# S04 acceptance — DSH compatibility and strict-plan evidence

S04 records the live DSH compatibility evidence and the boundary around
production enablement. The reference executable was DSH `0.1.5-rc.1`, run in a
disposable workspace.

## Live evidence completed

- ACP `initialize` succeeded.
- ACP `session/new` succeeded.
- ACP `session/prompt` using the default model returned `LIVE_OK` and
  `end_turn`.
- With the strict patch profile, shell/write probing exposed only the expected
  `glob`/`grep` operations; no target file was created.

## NOT_RUN / gate boundary

Production daemon routing is implemented behind the explicit
`enabled + spawn_supported + DSH_RUNTIME_PATH` gate, while the default remains
closed. Provider authentication/`hi` and
live Codex/ZCode host integration remain
**NOT_RUN**. The DSH production gate therefore remains closed; these live
probes do not constitute production spawn support or policy-plugin enablement.

## Production daemon smoke

In an isolated configuration with DSH `0.1.5-rc.1`, the daemon-routed build
path completed `spawn → wait → result → close`. The task returned
`DAEMON_LIVE_OK`, `COMPLETED`, and `resources_reaped=true`; the persisted
identity retained the opaque catalog model token, workspace path, and build
permission mode. This proves the configured build path, but does not cover
provider authentication/`hi` or host integration.

An isolated daemon-routed cancellation smoke reached `RUNNING`, issued
`cancel`, and returned `CANCELLED` with `resources_reaped=true`. Subsequent
`wait`, `result`, and `close` calls preserved the cancelled terminal state.

An isolated restart recovery smoke terminated the daemon while a DSH task was
`RUNNING`, restarted it with the same store and a fresh socket, and observed
the task as `TERMINAL / RUNTIME_LOST` with `resources_reaped=true`. No replay
was performed.

Explicit DSH `auth` and `hi` probes against the installed runtime were run in
an isolated workspace. Local discovery was `READY` at `0.1.5-rc.1`; auth
remained `UNKNOWN/auth_not_probed`, while the no-tool strict hi request was
classified `UNAVAILABLE/remote`. No credentials were changed or exposed.

The auth-only probe is side-effect free: it records `UNKNOWN/auth_not_probed`
without creating an ACP session or sending a prompt. The hi probe alone uses
the strict read-only profile.

An isolated daemon-routed strict-plan submission completed through ACP. The
model received a request to run a shell/write operation, reported that no
shell or write tool was available, and declined to claim success. The task
completed with resources reaped and the workspace remained empty. This proves
the strict refusal path; it does not authorize arbitrary write operations.
